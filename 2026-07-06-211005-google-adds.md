❯ ok jak by to fungovalo pres proxz                                             

● Jasně, vysvětlím princip, ať je jasné, proč to funguje.

  Proč je vůbec problém

  robots.txt je jen dobrovolná dohoda pro crawlery (Googlebot ji respektuje), ne
  ochrana přístupu. c.edsystem.cz má Disallow: /, takže:
  - Googlebot-Image → poslušně obrázek nestáhne.
  - Přímý HTTP request z našeho serveru → robots.txt vůbec neřeší, edsystem
  obrázek normálně vrátí (ověřeno, 200).

  Proxy tuhle asymetrii využije: obrázek necháme stáhnout náš server (kterému
  edsystem odpoví) a nabídneme ho z naší domény (kterou Googlebot smí
  crawlovat).

  Jak by tekl jeden request

  Googlebot-Image
     │  GET https://www.multishoping.eu/product-image/1104.jpg
     ▼
  [ náš server / multishoping.eu ]      ← robots.txt povoluje vše, projde
     │  1) ProId 1104 → z tabulky ProductImage vezme reálnou URL
     │       (https://c.edsystem.cz/IMGCACHE/_1/1104_0a.jpg)
     │  2) server-side stáhne bajty z edsystem (server-to-server, 200)
     │  3) uloží do cache (disk) + pošle zpět
     ▼
  Googlebot-Image dostane platný obrázek z povolené domény → schváleno ✅

  Pro Googlebota to vypadá, že obrázek hostujeme my — což je pravda, streamujeme
  ho z naší domény.

  Cache (aby to nezatěžovalo)

  - Cache-Control: public, max-age=... → Google i prohlížeče si obrázek drží.
  - Disková cache na našem serveru: první request stáhne z edsystem a uloží;
  další requesty (Googlebot re-crawl, návštěvníci) se servírují lokálně,
  edsystem se už nevolá.
  - Google projde ~79k obrázků jednorázově (rozloženě přes dny); s cache je to v
  pohodě.

  Kde proxy použít

  1. Feed image_link → vždy (kvůli „Obrázek nelze zobrazit"). Nutné.
  2. <img> na produktovém detailu → aby prošla i „kontrola kvality stránky" (66
  %), protože Google renderuje stránku a chce načíst i obrázky na ní.
    - Web pro běžné návštěvníky funguje i teď (prohlížeč robots.txt neřeší), ale
  kvůli Googlu je lepší i detail přepnout na proxy — s cache to výkon neohrozí.

  Ošetření krajních případů

  - edsystem vrátí 404 / chybu → proxy vrátí 404 (produkt bez obrázku se prostě
  neschválí, neshodí feed).
  - Streamujeme jen daný obrázek, Content-Type: image/jpeg.

  Pozn.: jsou to obrázky produktů z tvého katalogu (eD system), které eshop už
  teď veřejně zobrazuje — jen je nově servíruješ přes vlastní doménu, což je
  standardní postup.

  ---
  Dává to smysl? Pokud jo, postavím to (route + controller s diskovou cache,
  přepnu feed image_link a <img> na detailu na proxy) a nasadím na produkci.

  Dva háčky, které je fér zmínit

  1. Samba ≠ webserver. SMB je jen sdílení souborů. Aby to Google stáhl přes
  HTTP, stejně musí před tím běžet nginx/apache (buď na prod serveru s
  namountovaným SMB sharem, nebo webserver na NASu). Takže „na Sambě" = kde leží
  soubory, ale HTTP servírování je pořád potřeba.
  2. nas.multishoping.eu = nová subdoména → DNS + TLS certifikát + config 
  webserveru + vlastní robots.txt (musí povolit crawlery). Není to nutné pro
  crawlovatelnost (cesta na hlavní doméně stačí), ale jako dedikovaný image host
  je to hezčí.

  Moje doporučení — hybrid (nejlepší z obojího)

  Nechat stejnou URL /product-image/{proId}.jpg, ale přidat do ní cache na 
  disk/NAS:
  - první request → stáhne z edsystem a uloží na naše úložiště,
  - další requesty (Google re-crawl, návštěvníci) → servírují se z našeho 
  úložiště, edsystem se už nevolá.

  Tím se obrázky postupně zrcadlí k nám bez velkého jednorázového stahování a
  bez sync jobu — a URL zůstává stejná, takže v Merchant Center nic
  nepřenastavuješ. Později se dá klidně přepnout na images.multishoping.eu /
  CDN.

  Co teď

  Pro schválení produktů v Merchant Center to už řeší i současná proxy — obrázky
  jsou z naší domény, Googlebot je stáhne (ověřeno 200). Takže launch tím 
  neblokuj.

  Chceš, ať:
  - A) teď přidám tu cache-na-úložiště do existující proxy (lazy mirror na NAS —
  potřebuju vědět, kam je na prod serveru NAS namountovaný / cestu), nebo
  - B) necháme jednoduchou proxy pro rozjezd a plný mirror/CDN vyřešíme až po
  launchi?

  Rozhodni A/B — a jestli A, řekni mi mount path NASu na produkci.
