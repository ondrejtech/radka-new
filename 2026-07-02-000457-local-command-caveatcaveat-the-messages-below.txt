● Dobrá otázka — to je přesně to, co PayPal nabízí přes Advanced (Hosted) Card

● Ano — přesně tohle PayPal umí přes Advanced (Hosted) Card Fields. Zákazník
  zadá údaje karty přímo do tvého vlastního formuláře na webu a nemusí se nikam 
  přihlašovat. Notebook to potvrzuje, ale má jako zdroj jen README z GitHubu,
  takže ti to shrnu prakticky:

  Jak to funguje

  1. Frontend – PayPal JS SDK s components=card-fields vykreslí do tvých <div>
  kontejnerů bezpečné iframy pro číslo karty / expiraci / CVV. Citlivá data jdou
  přímo PayPalu (řeší PCI compliance za tebe), tvůj server je nikdy nevidí.
  2. Server (PHP) – tvůj backend dělá jen dvě věci:
    - createOrder (intent CAPTURE) → vrátí order ID, které pošleš na frontend
    - po odeslání formuláře captureOrder(orderId) → reálné stržení peněz

  Server je v tomhle scénáři stejný jako u běžného PayPal tlačítka — celý rozdíl
  je na frontendu (card-fields místo buttons).

  Důležité podmínky ⚠️

  - Schválení účtu: Business účet musí mít povolené Advanced Credit and Debit 
  Card Payments (ACDC). V sandboxu to bývá dostupné rovnou, v produkci to 
  podléhá schválení PayPalem a závisí na zemi účtu.
  - Dostupnost dle regionu – ACDC není ve všech zemích. Tohle je potřeba ověřit
  pro tvůj konkrétní účet (ČR/EU), protože ne všechny pokročilé funkce karet
  jsou v EU plně dostupné.

  Pozor na balíček v projektu

  Projekt techdomov používá blendbyte/paypal (fork srmklive), ne oficiální
  paypal/PayPal-PHP-Server-SDK z tohoto notebooku. Pro server část 
  (createOrder/capture) to nevadí — oba umí REST Orders API v2 a card fields
  jsou hlavně záležitost JS SDK. Jen je dobré vědět, že syntax volání se mezi
  balíčky liší.

  Plán

  1. Výměna balíčku

  - composer remove blendbyte/paypal
  - composer require paypal/paypal-server-sdk
  - Po instalaci ověřím přesné názvy tříd/namespace ve vendor/ (generované SDK —
  PaypalServerSdkClientBuilder, OrdersController, builder objekty) a teprve pak
  píšu kód proti ověřenému API.

  2. config/paypal.php

  - Oficiální SDK config nečte → pročistím soubor na to, co skutečně používáme:
  mode, sandbox/live credentials, webhook_id. Hodnoty čtu v service ručně. .env
  nesahám (mám zakázáno).

  3. PayPalService.php — přepis

  - Inicializace přes PayPalServerSDKClientBuilder +
  ClientCredentialsAuthBuilder, environment dle config('paypal.mode').
  - createOrder() → typované buildery (OrderRequestBuilder,
  PurchaseUnitRequestBuilder, AmountWithBreakdownBuilder), vrátí order ID + 
  approval link (potřeba pro oba toky).
  - captureOrder() → OrdersController::captureOrder, čtení z typovaných modelů
  (getResult()), ApiException/ErrorException místo polí; zachovám retry a
  INSTRUMENT_DECLINED logiku.
  - verifyWebhook() → ruční POST na /v1/notifications/verify-webhook-signature
  přes Laravel Http klienta (s access tokenem získaným z SDK / OAuth).

  4. Card-fields tok (nové)

  - Controller: přidat JSON endpointy — createOrder vracející {id} (pro
  card-fields callback) a capture vracející JSON výsledek (pro onApprove).
  - Routy: přidat pod stávající paypal / paypal.guest skupiny.
  - Config/route pro client-id: frontend potřebuje veřejný client-id → bezpečně
  předat do blade.
  - Frontend order.blade.php: ponechat stávající redirect tlačítko + přidat
  card-fields kontejnery (číslo karty / expirace / CVV) a JS SDK s
  components=buttons,card-fields.

  5. Beze změny

  - Order model (sloupce paypal_order_id, paypal_capture_id zůstávají), webhook
  route bez CSRF v bootstrap/app.php, InvoiceService.

  ⚠️ Upozornění

  - Card-fields (ACDC) v produkci pro CZ účet podléhá schválení PayPalem a
  nemusí být v ČR dostupné. V sandboxu to půjde testovat hned, produkce může
  vyžadovat aktivaci na účtu — to je mimo kód.

  Co bylo špatně

  celou šířku pod platebními metodami:
  - oddělený horní linkou (border-top), max. šířka 440px

  - číslo karty na celou šířku, platnost + CVV vedle sebe (každé 50 %), výška
  polí 44px
